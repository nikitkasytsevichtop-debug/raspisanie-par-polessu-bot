# Расписание занятий ПолесГУ — Telegram-бот

Telegram-бот расписания занятий преподавателя Полесского государственного университета. Самостоятельный проект Vercel: он не обращается ни к сайту-веб-приложению, ни к боту расписания спортивных объектов, и не делит с ними ни хранилище, ни cron.

## Что делает

- `/start` открывает единственную карточку расписания; все кнопки редактируют её, а не сыплют новыми сообщениями;
- карточка листается по дням и по неделям, вид переключается одной кнопкой;
- рядом с парами с сайта стоят и те, которых там нет, — занятия СМГ по расписанию кафедры;
- в полночь по Минску карточка сама переходит на новый день;
- каждые пять минут в рабочие часы бот сверяет расписание на сайте и присылает отдельное сообщение, когда оно изменилось, — с распознаванием переносов, а не голым списком «добавлено/удалено»;
- уведомления выключаются той же кнопкой на карточке; расписание при этом продолжает работать;
- хранит только `chat_id`, `message_id` карточки, выбранную дату, вид и переключатель уведомлений — в Upstash Redis.

## Источник данных

Расписание лежит на `polessu.by/ruz` и разложено по четырём страницам:

| Адрес | Что это |
|---|---|
| `/ruz/?q=<имя>&f=1` | 1 семестр, недели 1–20 |
| `/ruz/?q=<имя>&f=2` | 1 семестр, сессия (недели 21–24) |
| `/ruz/term2/?q=<имя>&f=1` | 2 семестр, недели 1–20 |
| `/ruz/term2/?q=<имя>&f=2` | 2 семестр, сессия |

Опрашиваются все четыре, даже когда три из них отвечают «Ничего не найдено». Так второй семестр и сессия появятся сами, без правки кода.

### Разбор страницы

Вёрстка машинная, поэтому текстовой эвристики здесь нет вовсе — в отличие от бота спортивных объектов, где страницы свёрстаны тремя разными способами.

Строка занятия несёт свои недели прямо в классах:

```html
<tr class="w1 w6 w7 w9 sad34e0f6">
  <td>13:30-14:50</td>
  <td>(2, 7-8, 10) Физическая культура - пр.</td>
  <td><span>Спорткомплекс ПолесГУ</span></td>
  <td><span><a href="?q=3DB97C422332A4CC&f=1">26БТ-1</a> <sup></sup></span></td>
</tr>
```

`w1 w6 w7 w9` — номера недель, `sad34e0f6` — хеш предмета. Строки `<tr class="wa">` задают день недели для всех следующих за ними. Номера недель дублируются текстом в скобках, но разбираются именно классы: в тексте недели записаны диапазонами («5-7»), а в классах — перечислением.

Календарные даты берутся из выпадающего списка недель того же документа:

```
#w0 → Неделя 1 (31.08-05.09)
#w1 → Неделя 2 (07.09-12.09)
```

Поэтому отдельные недели грузить не нужно: одна страница содержит весь семестр.

### Год

Года на странице нет вообще — недели подписаны как «31.08-05.09». Он восстанавливается двумя признаками сразу:

1. **Учебная неделя начинается с понедельника.** Из трёх кандидатов (прошлый, текущий, следующий год) остаются только те, где первая неделя приходится на понедельник. Мимо года этот признак почти наверняка не пройдёт.
2. **Близость к сегодняшнему дню** разводит оставшихся: без неё весенний семестр, выложенный осенью, уехал бы на год назад.

Внутри списка год увеличивается там, где месяц пошёл назад, — так семестр переживает переход через январь.

### Чего бот не выдумывает

Разбор различает три состояния источника, и мониторинг обязан их различать:

- **`ok`** — расписание разобрано;
- **`empty`** — сайт ответил, но преподавателя не показал ни на одной странице (сессия ещё не выложена — законное состояние);
- **`unavailable`** — сайт не ответил вовсе.

Рассылку об изменениях порождает только первое. Падение сайта и пустой ответ в снимке выглядят одинаково — как снятие всех пар разом, — поэтому при них снимок не перезаписывается и сравнение не выполняется.

Так же разведены и состояния даты в карточке. «Пар нет», «выходной» и «расписание на эту дату ещё не опубликовано» — три разных утверждения, и подменять последнее первым бот не должен. Воскресений в диапазонах недель нет (недели идут понедельник–суббота), поэтому день внутри семестра, но вне любой недели — это выходной, а не пробел в данных.

### Занятия вне сайта

Специальные медицинские группы (СМГ) кафедра ведёт по своему расписанию, и в ruz оно не попадает. Недельный шаблон лежит в `lib/extra-lessons.js`. Дни и время переписаны из сообщения кафедры как есть — так шаблон легко сверить с источником и заменить в следующем семестре:

```js
{
  from: '2026-09-14',
  to: '2026-12-26',
  subject: 'Физическая культура',
  kind: 'пр.',
  room: 'Гребная база 1 (218 зал)',
  groups: {
    'СМГ 18': 'пн 16:40, ср 18:10, чт 16:40',
    'СМГ 14': 'вт 18:10, ср 16:40, чт 18:10',
    'СМГ 13': 'пн 18:10, вт 16:40, ср 19:40',
  },
}
```

Шаблон повторяется каждую неделю с `from` по `to` включительно, и период может начаться или кончиться посреди недели. Конца занятия в сообщении нет. Его считает `lib/schedule.js` по длине пары в ПолесГУ — 80 минут, как у каждой строки сайта: 16:40–18:00, 18:10–19:30, 19:40–21:00.

Кусок, который не разобрался, пропускается с предупреждением в логе. Исключение здесь было бы хуже: опечатка в одном дне оставила бы без ответа весь бот. Чтобы опечатка не дошла до продакшена, тест разбирает настоящий шаблон и падает на первом же предупреждении.

Подмешиваются такие занятия только к настоящему расписанию, то есть при статусе `ok`. Когда сайт не ответил или ответил пустой страницей, карточка с одними СМГ выглядела бы полным днём, а не его частью, поэтому она по-прежнему говорит, что данных нет.

Если занятие совпало по времени с парой сайта, бот показывает обе. Спрятать одну значило бы решить за преподавателя, какая из них настоящая.

В снимок для уведомлений СМГ входят наравне с парами сайта. Поэтому правка шаблона уходит в рассылку как изменение расписания — с распознаванием переносов, как и правка на сайте. Если рассылка не нужна, поднимите `SNAPSHOT_VERSION`: первая проверка примет новое расписание за базовое и промолчит. Так был добавлен и сам шаблон.

## Интерфейс

Два ряда кнопок, по одному вопросу на ряд: куда смотреть — и чем управлять.

```
‹ ср 16        Сегодня        пт 18 ›
🗓 Неделя      🔔 вкл          ↻
```

В недельном виде первый ряд листает недели и подписан их номерами с сайта:

```
‹ Нед. 3     Эта неделя     Нед. 5 ›
📅 День       🔔 вкл          ↻
```

**Карточка дня** показывает пары с местом и группой, а между ними — окна:

```
четверг, 17 сентября
Неделя 3 · 4 пары · 10:05–16:25

10:05–11:25 · Физическая культура — пр.
📍 Спорткомплекс ПолесГУ · 👥 26БТ-1

⌛ окно 1 ч 50 мин

15:05–16:25 · Аквааэробика — пр.
🚪 ауд. 31 · 👥 23ФК-3
```

Окном считается разрыв от 35 минут: штатные перерывы между парами — 15 и 30 минут, всё длиннее означает пропущенную пару. Окно стоит строкой между парами, а не в шапке, — так видно, где именно в дне разрыв.

Номер аудитории и название корпуса подписаны по-разному (`🚪 ауд. 3430` и `📍 Спорткомплекс ПолесГУ`) — по виду значения, а не по списку известных мест: новый корпус тогда не придётся вносить в код.

Пустой день объясняет причину и подсказывает, когда пары будут снова: «занятий нет» без такой подсказки заставляет листать карточку вручную.

**Воскресенье** недельная карточка относит к предстоящей неделе, а не к прошедшей: в воскресенье смотрят вперёд. Шаг листания при этом остаётся ровным — каждое воскресенье сдвигается ровно на день, поэтому ±7 дней по-прежнему переводят на соседнюю неделю.

Бот хранит ID рабочей карточки. Повторный `/start` пересоздаёт её: старая удаляется, приходит свежая. Так команда гарантированно даёт видимый ответ даже после очистки истории «только у себя», когда старая карточка жива для бота, но невидима для пользователя. Настройки при этом сохраняются, а дата сбрасывается на сегодня: `/start` — это «покажи, что сейчас», а не «верни меня туда, где я листал неделю назад».

ID карточки и настройки лежат в разных ключах Redis намеренно. `/start` переписывает только `message_id`, кнопки — только настройки, поэтому одновременные запросы не могут затереть чужой ID. Карточка, потерявшая его, стала бы «сообщением, которого нет»: очередное фоновое обновление получило бы `message to edit not found`, а чат молча выпал бы из рассылки. Сами настройки лежат хешем, а не одним JSON-значением: листание дней тогда не задевает переключатель уведомлений и не требует чтения перед записью.

Действие, дата и вид едут в `callback_data` целиком (`d:2026-09-17:w`, 14 байт из разрешённых 64): у функции нет памяти между запросами, и кнопка обязана оставаться рабочей после любого холодного старта. Значения из хранилища нормализуются на чтении — неизвестный вид или битая дата не должны доехать до `callback_data`, иначе маршрутизация их не примет и карточка перестанет отвечать целиком, включая `/start`.

## Уведомления об изменениях

Upstash QStash вызывает `/api/check-changes` по расписанию `CRON_TZ=Europe/Minsk */5 6-21 * * *` — каждые пять минут с 06:00 до 21:55 по Минску, 192 вызова в сутки.

Круглосуточной проверки здесь нет намеренно. Суточный лимит QStash общий на весь аккаунт, а учебная часть правит расписание в рабочее время: ночная проверка тратила бы квоту, ничего не находя. Ретраев у расписания один вместо трёх по умолчанию — ретрай расходует сообщение наравне с обычным вызовом, а при пятиминутном шаге упорные повторы бессмысленны: следующий тик уже на подходе.

### Проверка в две ступени

Пять минут × четыре страницы — это 768 запросов в сутки к небольшому серверу университета, у которого в `robots.txt` стоит `Crawl-delay: 10`. Столько внимания странице, которую правят раз в несколько дней, не нужно, поэтому проверка идёт в две ступени.

Сначала **проба**: одна страница вместо четырёх. В её подвале стоит метка «Последние изменения вносились: 03.09.2026 16:19» — она общая по всему университету и одинакова на всех страницах, включая пустые. Если метка не сдвинулась с прошлой полной проверки, разбирать нечего и остальные три страницы не грузятся.

Метка общая, поэтому ложные срабатывания она даёт — её двигает и правка чужого расписания. Пропусков она не даёт, а для сторожа нужно ровно это: лишняя полная проверка стоит трёх запросов, пропущенная — потерянного изменения.

«Судя по всему» не гарантия, поэтому у сторожа есть потолок: полная проверка идёт не реже раза в полчаса и обязательно при смене суток, даже если метка стоит на месте. Битая отметка времени в пульсе считается просроченной — иначе одна кривая запись заперла бы сторож в закрытом положении навсегда. Если проба не удалась, проверка сразу идёт полной: молчащий сайт не повод считать, что ничего не изменилось.

Страницу, принесённую пробой, полный разбор переиспользует и второй раз за ней не ходит. В покое проверка стоит одного запроса вместо четырёх, а в сутки выходит около 290 вместо 768 — меньше, чем при получасовом шаге без сторожа, но с шестикратно более быстрой реакцией.

Пульс (`ruz:pulse` — метка, время и день последней полной проверки) лежит отдельным ключом от снимка: сторож читает его на каждой проверке, а снимок весит под сорок килобайт, и таскать их ради экономии запросов к сайту значило бы платить трафиком к Redis.

### Лимиты

| Ресурс | Бесплатный лимит | Расход бота |
|---|---|---|
| QStash — сообщений в сутки | 1000 на аккаунт | 192 |
| QStash — активных расписаний | 10 на аккаунт | 1 |
| Upstash Redis — команд в месяц | 500 000 | ~40 000 |
| Vercel Hobby — вызовов функций в месяц | 1 000 000 | ~6 000 |

Лимит QStash общий на аккаунт: при добавлении новых ботов бюджет считается вместе с ними.

Сравнивается нормализованное расписание, а не HTML-разметка. Первая проверка сохраняет исходное состояние и молчит.

### Переносы вместо «добавлено/удалено»

Голый diff для расписания читается плохо: перенос пары выглядит как две несвязанные строки, и сшивать их приходится глазами. Поэтому бот сшивает сам — по предмету, виду занятия и группе (дата, время и аудитория в этот ключ не входят: именно они и меняются при переносе):

```
🔔 Расписание изменилось

🕐 Аквааэробика — пр. · 23ФК-1
   чт 17.09: 10:05–11:25 → 15:05–16:25
🚪 Физическая культура — пр. · 26БТ-1
   вт 22.09: Спорткомплекс → ауд. 3431
🔀 Информационный час · 24ТД-1
   пт 18.09: 08:30–09:50 → 13:30–14:50 · ауд. 3507 → ауд. 3431
📆 Аквааэробика — пр. · 23ТД-1
   ср 16.09 10:05 → сб 19.09 10:05
➕ Плавание — лек. · 27ФК-9
   ср 16.09 · 15:05–16:25 · ауд. 3405
❗ чт 24.09 — сняты все пары (3)
```

Совпадение по дате берётся первым: правка внутри дня вероятнее переноса на другой день, и иначе пара могла бы «уехать» к чужому дню с тем же временем. День, у которого сняли всё, схлопывается в одну строку — это одно событие, а не пять.

Публикация целого периода (сессия, второй семестр) сворачивается в сводку «Опубликовано расписание: добавлено N пар, 12.01 – 06.03»: разворачивать её в список из полусотни строк бессмысленно, читать никто не станет. Длинный список изменений обрезается на двенадцати строках со счётчиком остатка.

Сравниваются только сегодняшний день и будущее. Иначе смена суток сама по себе выглядела бы как изменение на сайте: вчерашние пары никуда не делись, но говорить о них уже незачем.

Формат снимка помечен номером версии (`SNAPSHOT_VERSION` в `lib/change-monitor.js`). После его изменения первая проверка снова считается базовой и молчит — так правка парсера не уезжает в рассылку под видом правки расписания. Номер недели и семестр в снимок не идут: перенумерация недель на сайте не должна выглядеть как изменение расписания.

Первая проверка нового дня обновляет все зарегистрированные карточки, даже если расписание не менялось: иначе до первого нажатия кнопки они показывали бы вчерашнюю дату.

## Деплой

1. Создайте **отдельный** GitHub-репозиторий из этой папки и импортируйте его в Vercel как новый проект.
2. В Vercel Marketplace подключите **Upstash Redis** к этому проекту. Интеграция добавит `KV_REST_API_URL` и `KV_REST_API_TOKEN` автоматически; при прямом подключении Upstash используются `UPSTASH_REDIS_REST_URL` и `UPSTASH_REDIS_REST_TOKEN`.
3. В Vercel → Settings → Environment Variables добавьте остальные значения из `.env.example`:
   - `TELEGRAM_BOT_TOKEN` — токен от @BotFather;
   - `TELEGRAM_WEBHOOK_SECRET` — новая случайная строка из букв, цифр, `_` и `-`;
   - `APP_URL` — URL именно этого проекта Vercel, без завершающего `/`;
   - `CRON_SECRET` — отдельная случайная строка не короче 32 символов;
   - `CHANGE_CHECK_SECRET` — отдельная случайная строка не короче 32 символов для QStash.
4. Сделайте production redeploy. Расписание cron из `vercel.json` создаётся только для production-деплоя.
5. Создайте расписание QStash — скриптом из репозитория:

   ```bash
   node scripts/qstash.js create
   ```

   Скрипт читает `QSTASH_TOKEN`, `QSTASH_URL`, `APP_URL` и `CHANGE_CHECK_SECRET` из `.env.local`, отказывается плодить дубли на один адрес и передаёт секрет заголовком `Upstash-Forward-Authorization`, поэтому эндпоинт остаётся закрытым снаружи. `node scripts/qstash.js list` показывает расписания аккаунта, `delete <id>` убирает.
6. Однократно откройте в браузере:

   `https://<ваш-домен>/api/telegram?setup=<TELEGRAM_WEBHOOK_SECRET>`

   В ответе должно быть `"ok": true`. Операция зарегистрирует webhook и команды и снимет описание бота (`setMyDescription` с пустой строкой); старый webhook будет заменён автоматически.
7. Напишите боту `/start`.

### Автор коммита

Проект связан с GitHub, поэтому на плане Hobby Vercel проверяет автора последнего коммита и требует, чтобы он совпадал с владельцем аккаунта. Сверка идёт по email через GitHub.

Если `git config user.email` не задан, git подставляет машинный адрес вида `nikita@MacBook-Air.local`. GitHub такой коммит не привязывает ни к кому, и деплой встаёт в состояние `BLOCKED` с причиной «Vercel couldn't find a Git account for the commit author» — без единой строки в логах сборки, потому что сборка даже не начиналась. В `vercel ls` при этом видно `UNKNOWN`, а настоящее состояние отдаёт только REST API:

```bash
curl -H "authorization: Bearer $VERCEL_TOKEN" \
  "https://api.vercel.com/v13/deployments/<url>?teamId=<team>" | grep readyStateReason
```

В этом репозитории адрес задан локально:

```bash
git config user.email 93950600+NikitaSytsevich@users.noreply.github.com
```

Адрес noreply GitHub выбран намеренно: он привязан к аккаунту, и при этом настоящая почта не попадает в историю коммитов.

Ссылку из шага 6 не передавайте другим и не сохраняйте в публичных каналах: секрет в ней нужен только для начальной настройки. После успешной регистрации его можно заменить новой переменной и повторить setup.

## Локальная проверка

```bash
npm install
npm test
npx vercel dev
```

Публичный HTTPS-адрес нужен Telegram для webhook, поэтому локальный сервер сам по себе бота не подключит.

Тесты не ходят в сеть: разбор проверяется на сохранённой странице (`test/fixtures/`), а сквозные сценарии — на странице, которую `test/helpers.js` строит вокруг сегодняшнего дня. Фикстура с жёстко зашитым семестром однажды уехала бы от «сегодня» на годы, и восстановление года выбрало бы другой.

## Расписания проверок

| Что | Когда | Зачем |
|---|---|---|
| QStash → `/api/check-changes` | `CRON_TZ=Europe/Minsk */5 6-21 * * *` | сверка расписания, рассылка, переход карточки на новый день |
| Vercel Cron → `/api/daily-refresh` | `0 4 * * *` (07:00 Минск) | резервное обновление карточек и перевод их на новый день |

Ночью проверок нет, поэтому на новый день карточку переводит первый утренний вызов — QStash в 06:00 или суточный Vercel Cron в 07:00. Оба маршрута закрыты своим секретом в заголовке `Authorization` и снаружи недоступны. Разметку карточки оба собирают одной функцией `cardView` из `lib/format.js`.

## Смена преподавателя

Кого показывает бот, задаёт константа `TEACHER` в `lib/schedule.js`. Поиск на сайте нестрогий — хватило бы и одной фамилии, но полное имя защищает от однофамильцев. После смены имени поднимите `SNAPSHOT_VERSION`, иначе первая же проверка разошлёт чужое расписание как «изменения».
